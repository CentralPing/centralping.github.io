Enforces per-client request rate limits using a sliding-window counter.
On allowed requests, injects `X-RateLimit-*` response headers. On limited
requests, returns `429 Too Many Requests` with a `Retry-After` value.

The store is pluggable — any object implementing
`hit(key, windowMs) → { count, resetMs }` can replace the built-in
`MemoryStore` for Redis-backed or distributed rate limiting.

**Pipeline stage:** Negotiation

## Import

```js
import { rateLimit } from "@centralping/ergo";
```

## Options

| Option | Type | Default | Description |
| ------ | ---- | ------- | ----------- |
| `max` | `number` | `100` | Maximum requests per window |
| `windowMs` | `number` | `60000` (1 min) | Window duration in milliseconds |
| `store` | `object` | `MemoryStore` | Pluggable store with `hit(key, windowMs)` interface |
| `keyGenerator` | `function` | `defaultKeyGenerator` | `(req) => string` — client identifier (default: `req.socket.remoteAddress`) |

## Return Value

### Allowed Request

```js
{
  response: {
    headers: [
      ["X-RateLimit-Limit", "100"],
      ["X-RateLimit-Remaining", "99"],
      ["X-RateLimit-Reset", "1717041600"]
    ]
  }
}
```

### Limited Request

```js
{
  response: {
    statusCode: 429,
    retryAfter: 30
  }
}
```

`send()` automatically sets the `Retry-After` header and formats the
RFC 9457 error body.

## Error Responses

| Status | Condition |
| ------ | --------- |
| **429 Too Many Requests** | Request count exceeds `max` within `windowMs` |

## Custom Store

The `store` option accepts any object that implements a single method:

| Method | Signature | Returns |
| ------ | --------- | ------- |
| `hit` | `(key: string, windowMs: number) => object` | `{ count: number, resetMs: number }` |

| Return Field | Type | Meaning |
| ------------ | ---- | ------- |
| `count` | `number` | Total hits recorded for `key` within the current window |
| `resetMs` | `number` | Milliseconds until the oldest entry in the window expires |

The middleware calls `store.hit(key, windowMs)` once per request. The
store is responsible for recording the hit, pruning expired entries,
and returning the current state. No other methods are called.

### MemoryStore Options

The built-in `MemoryStore` accepts optional configuration:

| Option | Type | Default | Description |
| ------ | ---- | ------- | ----------- |
| `maxKeys` | `number` | `10000` | Maximum tracked keys before FIFO eviction. When exceeded, the oldest key is silently removed. |
| `now` | `function` | `Date.now` | Clock function returning current time in milliseconds. Useful for deterministic testing. |

```js
import { MemoryStore } from "@centralping/ergo/lib/rate-limit";

const store = new MemoryStore({ maxKeys: 50_000 });
```

### Redis Store Example

For multi-instance deployments, implement the `hit()` contract with a
shared data store. This example uses
[ioredis](https://www.npmjs.com/package/ioredis) with sorted sets:

```js
import Redis from "ioredis";

class RedisStore {
  constructor(redis) {
    this.redis = redis;
  }

  async hit(key, windowMs) {
    const now = Date.now();
    const windowKey = `rl:${key}`;
    const cutoff = now - windowMs;

    const pipeline = this.redis.pipeline();
    pipeline.zremrangebyscore(windowKey, 0, cutoff);
    pipeline.zadd(windowKey, now, `${now}:${Math.random()}`);
    pipeline.zcard(windowKey);
    pipeline.zrange(windowKey, 0, 0, "WITHSCORES");
    pipeline.pexpire(windowKey, windowMs);

    const results = await pipeline.exec();
    const count = results[2][1];
    const oldest = results[3][1];
    const oldestScore = oldest.length >= 2 ? Number(oldest[1]) : now;
    const resetMs = Math.max(0, oldestScore + windowMs - now);

    return { count, resetMs };
  }
}
```

### When to Use a Shared Store

| Scenario | Recommended Store |
| -------- | ----------------- |
| Single process, development, or testing | `MemoryStore` (default) — no external dependencies |
| Multiple instances behind a load balancer | Redis or another shared store — counters must be visible across instances |
| Serverless / ephemeral containers | Shared store — process restarts reset in-memory counters |

<Aside type="caution" title="Process restart resets in-memory counters">
  `MemoryStore` state lives in the Node.js process. Restarting the
  server (deploy, crash, autoscale) resets all counters to zero. If
  consistent rate limiting across restarts is required, use a shared
  store.
</Aside>

### Proxy Awareness

<Aside type="caution" title="Default key is the proxy's IP behind a reverse proxy">
  The default `keyGenerator` uses `req.socket.remoteAddress`, which
  resolves to the **proxy's IP** when your application runs behind
  nginx, a cloud load balancer, or any reverse proxy. All clients
  share a single rate-limit bucket, making rate limiting ineffective.
</Aside>

When deploying behind a reverse proxy, provide a custom `keyGenerator`
that reads the forwarded client IP:

```js
rateLimit({
  keyGenerator: (req) => {
    const forwarded = req.headers["x-forwarded-for"];
    return forwarded
      ? forwarded.split(",")[0].trim()
      : req.socket.remoteAddress;
  },
})
```

<Aside type="caution" title="Only trust X-Forwarded-For behind a proxy you control">
  When the application is directly exposed to the internet (no reverse
  proxy), clients can set `X-Forwarded-For` to any value — bypassing
  rate limiting entirely. Only use a forwarded-header `keyGenerator`
  when your app runs behind a proxy you control.
</Aside>

This applies to both pipeline-level rate limiting
(`defaults.rateLimit` or per-route `rateLimit` in ergo-router) and
transport-level rate limiting (`transport.rateLimit`). The
[`trustProxy`](/packages/ergo-router/) router transport option does
**not** automatically make rate limiting proxy-aware — it only affects
request IDs and HSTS. A custom `keyGenerator` is always required for
correct per-client rate limiting behind a proxy.

## ergo-router Configuration

### Precedence

Per-route `rateLimit` config follows
[Config Resolution](/packages/ergo-router/#config-resolution) semantics:

| Config Level | Behavior |
| ------------ | -------- |
| Route `rateLimit: { max, windowMs }` | Overrides defaults for this route (shallow replace) |
| Route `rateLimit: false` | Disables rate limiting for this route |
| Route `rateLimit: undefined` (omitted) | Inherits from `defaults.rateLimit` |
| `defaults.rateLimit: { max, windowMs }` | Applied to every route that does not override |
| `defaults.rateLimit: undefined` (omitted) | No pipeline-level rate limiting |

<Aside type="caution" title="Transport vs. pipeline rate limiting">
  Rate limiting exists at **two independent levels** in ergo-router:

  - **Transport-level** (`transport.rateLimit`) — runs before routing on
    every request. Protects the server as a whole. Uses `res.setHeader()`
    directly.
  - **Pipeline-level** (`defaults.rateLimit` or per-route `rateLimit`) —
    runs inside the pipeline after routing. Protects individual resources.
    Returns rate limit headers via the response accumulator.

  Both can be active simultaneously. A request that passes the transport
  limit can still be rejected by a stricter pipeline limit on a specific
  route.
</Aside>

### Presets Interaction

Only [`presets.public`](/packages/ergo-router/#presets) includes
transport-level rate limiting (`transport.rateLimit: {}` with built-in
defaults of 100 requests per 60 seconds). The `jsonApi`, `sse`, and
`webhooks` presets do not include rate limiting at either level.

To add pipeline-level rate limiting when using a preset:

```js
import createRouter, { presets } from "@centralping/ergo-router";

const router = createRouter({
  ...presets.jsonApi,
  defaults: {
    ...presets.jsonApi.defaults,
    rateLimit: { max: 200, windowMs: 60_000 },
  },
});
```
