## The Fast Fail Principle

Every HTTP request passes through four ordered stages. A failure at any stage
immediately returns a standards-compliant error response — no downstream work
is wasted.

<CardGrid>
  <Card title="1. Negotiation" icon="approve-check">
    Content type, language, and encoding negotiation per [RFC 9110 §12.5](https://www.rfc-editor.org/rfc/rfc9110#section-12.5).
    Rate limiting and security headers run here — resource exhaustion is
    prevented before any processing begins.
  </Card>
  <Card title="2. Authorization" icon="warning">
    Bearer/Basic authentication per [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750) / [RFC 7617](https://www.rfc-editor.org/rfc/rfc7617). Unauthorized requests
    are rejected before body parsing, preventing DoS from large payloads on
    unauthenticated requests.
  </Card>
  <Card title="3. Validation" icon="pencil">
    JSON Schema body validation, query parameter parsing, and input
    sanitization. Bounded parsing defaults protect against allocation bombs.
    Malformed requests fail before execution.
  </Card>
  <Card title="4. Execution" icon="rocket">
    Only valid, authorized, properly-negotiated requests reach your handler.
    Responses use [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) Problem Details for errors.
  </Card>
</CardGrid>

<Aside type="tip" title="Secure by Default">
  ergo's pipeline structure and conservative defaults address the
  [OWASP API Security Top 10](https://owasp.org/API-Security/) — from
  prototype pollution prevention to decompression bomb protection. You don't
  opt _into_ security; you'd have to opt _out_.
  [Learn more →](/concepts/security/)
</Aside>
